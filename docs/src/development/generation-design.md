# Generation design

This chapter records why the language, the manifest, and the generator work as they do, and what was rejected. [Code generation](../concepts/generation.md) says what they do. [Messages and encodings](../concepts/messages.md) covers the message rules.

## A graph file, with one parser

`graph!` takes Rust types, so the compiler is its only resolver, and a mistake appears as a type error in expanded code. A composed graph needs names checked before anything compiles: do the edges agree, does each name mean one message, which line is wrong. A graph file has the body of `graph!` with message names in place of types.

- **One parser.** `graph!` and the generator read the same grammar through `gdl-syntax`. `gdl-macros` is a proc-macro crate, and a crate cannot import from one, so the parser is a separate crate. Two parsers would accept different graphs.
- **A depth bound before syn.** syn recurses once per level of a type, and once per bracket when it builds its token buffer. The composer parses a draft's graph in its own process, so text deep enough would abort the server. `Graph::parse` first walks the tokens with a stack of its own, and refuses text that nests past `MAX_DEPTH` (16) with a problem at the token that goes too deep. The walk costs one pass over the tokens. A bigger stack was rejected: a deeper text still crashes, and `gdl-syntax` builds for wasm, so it cannot take `stacker`. A check on the parsed types was rejected because syn's token buffer recurses before any type is parsed. The count is an upper bound on syn's recursion: brackets, prefix operators, and keywords that start an expression are levels, each step of a chain (a binary operator, a postfix, an `else if`) is an eighth of one, since the tree syn builds for it nests, and what counts lasts until the next sibling (`gdl_syntax::check_depth` has the rules). It cannot tell a `<` from a comparison, so it can count too much, but a graph needs no deep type. The source reader runs the same walk with a limit of its own, 4,096, which admits what rustc builds with default settings ([Known limitations](../operations/limitations.md#the-reader-reads-a-source-file-at-most-4096-levels-deep)).
- **The generated contract writes the resolved path.** It prints the `graph!` body from the checked model, never by replacing names in the file's text, because a node can be named like a message. Each message is a rooted path (`::chat_protocols::Words`), with a keyword segment escaped. The contract hash covers the type as written, so a name that resolves to a different crate changes the hash. A test holds that.
- **Public paths only.** The contract names a path that code outside the crate can use. A type defined in a private module must be exported, and resolution says so. A contract that named a private path would fail to compile (E0603) in a file the user did not write.
- **Open.** The graph's author sets `schema`, and the owner of an external protocols crate can change a wire form without that author knowing. Nothing detects it.

## Names the macro introduces

The port types are the caller's tokens, so a name the expansion adds could capture or be captured by them.

- Every name the expansion introduces starts with `__gdl` or `__Gdl`, parameters included. A parameter is a pattern, and a caller's constant of that name would turn into a constant pattern. Each kind of introduced name (slot generics, setter generics, node locals, hop locals) has its own prefix, so a node's name cannot make two equal.
- The expansion writes the caller's port types only at the invocation's own level, never inside the generated `nodes` module, where `super::` and a node marker change what a type names.
- Every other path is rooted: `::std`, `::core`, or the path `graph!` passes as `$crate`.
- The wire probe's method is `__gdl_codec`, not `codec`. The probe call sits in the caller's scope, and a caller's trait with a `codec` method made the call ambiguous.
- The probe runs only at concrete types. Inside a generic helper, autoref selection would always take the fallback.
- A diagram uses generated identifiers (`n0`, `s0`) and puts names only in labels. A node may be named like a keyword of either format (`end` in Mermaid), and a segment name may hold any character. In DOT the edge back into each hop's outer end has `constraint=false`, so the response path does not decide the ranks. Mermaid styles a link by its position, so one `linkStyle` line lists the positions of the crossing links.

## A portable model

The composer applies the generator's rules while the user draws. Those rules were in `gdl`, which depends on velo and tokio. They now live in `gdl-model` (serde and toml only): the roles, the manifest, placement, layouts, the crossing report, the diagrams, and the hashes. `gdl-syntax` depends on `gdl-model`, so there is one `Role`, and `syn` stays out of the runtime and every segment binary. `gdl-model` and `gdl-syntax` build for `wasm32-unknown-unknown`.

- **The composer's rules run on the server.** The wasm build stays tested and is not shipped, because `wasm-bindgen-cli` is not available offline. There is still one copy of each rule. A dependency test, which runs everywhere, catches a runtime dependency creeping in. The wasm build test runs when the target is installed and says how to add it when it is not.
- **`gdl-message` does not build for wasm.** `linkme` has no wasm support, so the portable crates must not depend on it. The generator depends on `gdl-model`, not `gdl`, so it builds without the runtime.

## A graph spec compiles nothing

The manifest of a contract spec comes from compiling the contract, because the macro produces it. A server that cannot build a crate that needs CUDA could then not build any contract that names one of its messages. For a graph spec the manifest is built from the graph file, the resolution, and the reader's wire capability and encoding. The builder spells each type as the compiler prints a rooted path, because the hash covers that spelling.

- **Rejected: a token walk that `graph!` would share.** It would remove the second copy of the spelling. It would also risk the hashes of contracts that name types other than messages, which `graph!` spells as the compiler does. The model's builder writes only message paths and `()`, whose spelling it controls. A test compiles the generated contract and holds its manifest, hash included, equal to the model's.
- **Accepted regression.** The reader decides wire capability, not the probe. If it misses a type's serde impls, for example impls that a macro writes, the generator refuses a cut that would work. The opposite error is covered by the crossing assertions, which fail the segment's build and name the crossing.
- **The dump program.** A contract spec still builds a throwaway program that depends on the contract and prints the manifest as TOML, so the program needs no dependency but the contract. Every dump in a target directory builds the same program path. A private source directory per run did not stop a concurrent dump from replacing the program between its build and its run. A lock file in the target directory (`gdl-gen/dump.lock`) is now held from writing the program until it has run, with one fixed source path under the lock. A test holds the lock and checks a second dump waits. The program starts from the lock of the contract's workspace, as the `--verify` program does. With no lock, Cargo resolves the program anew: it reads crates.io's index even when every crate is in its cache, and it may build newer versions than the workspace does. The test that compiles a graph spec's contract seeds it from the gdl workspace's lock, because the generated contract has no workspace and the gdl runtime brings most of its crates.

## Crates, not Cargo features

Native link requirements apply whenever a crate is a dependency, and Cargo unifies features across packages built together. A segment that should not link an implementation's native library cannot be protected by a feature. Separate implementation crates, one set per segment crate, are the only reliable isolation. A sentinel crate stands in for a heavy native dependency of the engine in `examples/chat`, and a test checks that only the engine segment's dependency tree contains it.

Emitted code is checked only when a generated crate builds. The segment `main` once named `Arc` without importing it, and no test built the crate. The lifecycle every `main` repeats is therefore one runtime function, tested once. [Lifecycle design](lifecycle-design.md) has the rest.

## Hub discovery on request

Hub discovery brings the hub client and its HTTP stack. Only a spec with a `[deployment]` table, or `compose`, asks the generated crates for the `hub` feature. An export without one carries no hub client.

## Build

`cargo gdl build` generates into the target directory and builds there. These were the choices.

- **Write only what changed.** Each run renders every file, and writes only the files whose text differs, through the same writer as `generate`. Rejected: delete the directory and write it again. Every file's time would change, so Cargo would rebuild and relink every segment, and a fat LTO link is most of a release build.
- **One workspace.** One `cargo build` compiles each shared dependency once and links the segments in parallel. The cost is feature unification, the failure in "Crates, not Cargo features": a segment can build here with a feature only another segment turns on, and fail in its image. `generate` into a user's workspace already has that cost. Rejected: one workspace per segment, as `export` writes. It needs a resolve and a `cargo build` for each segment, and links them one after another.
- **The compose code for crates by path.** The patches, the gdl patch, and the lock steps are those of `compose --local`, called with a mode that skips the image context's checks. Rejected: a second copy, since two copies of one rule drift.
- **A directory per spec, a lock per target directory.** Specs of one graph each mark the other's crates stale in a shared directory. Their binaries can share a name, which Cargo writes to one path, and Cargo's lock ends before the copy.
- **A record of each copy.** A build removes or writes over a binary in `--out` only while the binary's size and time match what it copied. A name alone would let it remove a file someone put there.
- **The lock as the user's.** The workspace's lock starts from the lock of the workspace that holds the spec. Starting again on every run would undo what Cargo writes. Rejected: `--locked` reads of the user's crates, which would fail the usual loop of editing a node's `Cargo.toml` and building.
- **Rejected: a `build.rs`.** A build script cannot add packages to a build or make another package's binary.
- **Rejected: `generate --out` adding workspace members.** It writes the user's `Cargo.toml`, and generated crates in the source tree drift.

## Export

- **One crate per segment, each its own workspace.** A shared workspace would unify features and resolve one dependency set for all segments, which is the failure above. The cost is one `cargo build` per segment. `build-all.sh` runs them into one `CARGO_TARGET_DIR` so they share a cache.
- **Dependencies as the spec gives them.** Versions and revisions stay as written. A directory becomes an absolute path. Which crate is inside the archive is decided by what was generated, never by a path's place on disk. Rejected: vendoring, which breaks crates that inherit from their workspace, and refusing directories, which makes export useless for local development.
- **Reproducible bytes.** A `.tar.gz` with sorted entries, zero times and owners, and a gzip header without a time. Two exports of one spec can then be tested by equality, and are the same on every machine.
- **An empty `[workspace]` in each manifest.** An archive expanded inside another workspace must still build.
- **No lockfile.** The first build writes one per segment. The cost is that images built later can resolve newer dependencies. Pinning is not done.
- **`export` is its own command.** It renders in memory with no temporary directory, so each command has one path policy.
- **`gdl` by `git` and `rev`.** gdl is not published, and an archive that a server writes must name it from anywhere.

### Images

An image needs everything in its build context. A directory on the exporting machine is not in the context, so an archive gets Dockerfiles only when gdl and every listed crate can be fetched anywhere, by a version or a revision. A contract spec's contract is a directory, so such a spec never gets them. The Dockerfile builds in the Rust image and runs the binary in a slim Debian image. The runtime image may need more than the binary, such as CA certificates for TLS, which a first real build will show. Publishing is not built: the registry, the credentials, and whether to push at all are open.

An earlier Compose design copied non-ignored files of a Git worktree into the bundle, and kept the original absolute path inside the builder so path dependencies resolved. It was replaced. A local source does not travel to a Docker host, and a bundle should hold only generated files. Deploy now accepts only Git or crates.io packages, and names the local ones to re-import.

`cargo gdl compose --local` amends that rule for one case: testing code that is not pushed. Docker Compose is the test path for a deployment, and code that is not pushed has no Git revision that an image build can fetch. With `--local`, the images build the crates that the spec names by path, and gdl and its hub from `[gdl] path`, from a build context outside the bundle: the nearest directory that holds the bundle, those crates, and the Cargo workspace of each. The bundle still holds only generated files, and names the context by a relative path. So the bundle builds only on the machine that wrote it, and it says so. The default mode and the composer stay Git or crates.io only, so a bundle that the composer writes or downloads still builds anywhere. The snapshot design was not brought back: a copy of the sources in the bundle goes stale at the next edit, and the context reads the sources as they are. A second Compose path was also tried and dropped: `generate` wrote a Compose file beside the segment crates, whose segments met in a roster directory on a shared volume instead of through a hub. It duplicated `cargo gdl compose` with another discovery, and two forms of one deployment drift apart. It also ran one deployment per roster: a segment that restarted, or a second run of a source, found more instances than the roster expected.

- **Relative paths, and a workspace per manifest.** The generated manifests name each crate relative to themselves, so that the paths resolve under the image's `/app` as they do on disk. Each manifest is its own workspace, since the bundle usually sits in a workspace, under its `target/`.
- **A lock written on the host.** `cargo gdl compose --local` writes each segment's `Cargo.lock` on the host, which can fetch every source the segment names. The lock starts from the lock of the workspace that holds `[gdl] path`. A fresh resolve would take the newest commit of each Git dependency, such as velo's branch, not the commit the runtime was tested with. Each image builds with `cargo build --locked`, so it resolves nothing: an image build has no SSH agent and no credentials. The host's Rust can be newer than the image's, so each segment's manifest gives `gdl-runtime`'s `rust-version`, and Cargo picks each new dependency for that Rust. Cargo runs on the host in the context's root, as the image build runs in `/app`, so that both read the same Cargo configuration, such as a registry that a node crate names. The hub builds with `cargo install --path --locked` from the same workspace. The first form copied gdl's lock into the segment in the image build, and resolved the rest there. That resolve fetched each Git source again, and failed for a source that needs SSH.
- **One copy of gdl.** A node crate in another repository can take gdl from Git, while the segment takes gdl from `[gdl] path`. The segment then builds two copies of gdl, whose types do not match. So each segment's manifest has a `[patch.<source>]` table for each gdl package that a crate the segment reaches by path takes from another source. The table gives the package from `[gdl] path`. The generator reads those sources with `cargo metadata --no-deps`, which fetches nothing. It skips a crate whose workspace that command cannot read, such as a crate whose own dev-dependency is not there, since a build never reads a dependency's dev-dependencies. A segment whose resolve still holds a second copy is refused ([limitations](../operations/limitations.md#a-bundle-of-local-sources-patches-gdl-only-where-a-crate-it-reaches-by-path-names-it)).
- **The host's patches.** Cargo reads `[patch]` only from the workspace it builds. A segment is a workspace of its own, so it does not see the patches of a node crate's workspace. The segment would then take another copy of a patched crate, or fail to resolve one that only the patch provides. So each segment's manifest also carries the `[patch]` entries of the workspace of each crate that a generated manifest names by path: the node crates, and gdl's own workspace through `gdl-runtime`. A path is written from the segment, with its `..` steps applied as Cargo applies them, and the context holds the crate it names and, through a symlink, its target. A Git entry stays a Git entry, and a version alone stays a version. Each source gets one table, and two keys that Cargo takes for one source, such as `crates-io` and crates.io's index URL, share it. A host entry that patches a gdl package, by its name or by `package`, is left out from any source. The segment builds one copy of gdl, from `[gdl] path`, and gdl's own entries cover each source that a crate it reaches takes gdl from. A host entry that has the name of one of gdl's entries in the same table is left out too, since TOML cannot hold the name twice. Two workspaces that patch one name of one source in different ways are refused: the segment can take only one, and the other host would build something else. The segment's lock starts from gdl's lock, which can hold a patched crate at a version that the patch does not give. Cargo then keeps that version and leaves the patch unused. So when the host's lock uses a patch that the segment's lock leaves unused, the generator moves the crate to the patch's version with `cargo update --precise`, and refuses the segment if the patch stays unused. The patches of a crate that is reached only through another crate are not carried, because the host does not apply them either ([limitations](../operations/limitations.md#a-bundle-of-local-sources-carries-only-the-patches-of-its-node-crates-workspaces)).
- **An ignore file per Dockerfile.** Build output and Git history stay out of the context. A bundle under a `target` directory is let back in.

## Encodings

Each application message selects named MessagePack (the default), positional MessagePack, or JSON. The envelope version is 4, which separates this wire contract from earlier builds.

- **Named maps are the default** because they keep an omitted optional field, including in nested structs. Positional arrays stay opt-in because they need a fixed layout, and the wire probe checks serde traits, not that each value round-trips.
- **One parser** reads the annotation for the derive and for the source reader, so the catalogue, resolution, exports, and manifests carry the same encoding.
- **The hash covers the encoding and its revision**, so a codec change cannot meet a peer that expects another one.
- **A streamed request selects head and items apart**, by syntax.
- **Typed selectors take the head's encoding from the edge's codec,** including when the destination slot is absent.
- **Edges pick monomorphized function pointers once.** No item pays for a lookup or a boxed value.

## Service clients

A service with several entries gets one typed client for each entry. `Client` erases the generated pipeline type at the service boundary, which adds one boxed future to each public call. Pipeline stages keep their concrete types. This is a construction and API choice, not a performance claim. The composer lowers each enabled endpoint to a public typed source root followed by ordinary graph nodes, so the compiler and the runtime check the topology the cutter shows. [Hosted frontends](../guides/frontends.md) has the user-facing form.

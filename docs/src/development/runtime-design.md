# Runtime design

This chapter records why the runtime is built the way it is: each decision, the alternative that was rejected, and what that alternative would cost. It also lists designs that were built and then removed, and the hazards that no test covers yet. Read [Crossing segments](../concepts/crossings.md), [Requests, attempts, and deadlines](../concepts/requests.md), [Streamed requests](../concepts/streamed-requests.md), and [Admission and egress](../concepts/admission.md) first. They say what the runtime does.

## Transport: velo directly, behind one module

The runtime calls velo directly. Every velo call lives in one internal module, `gdl-runtime`'s `dist/fabric.rs`. Generated code and node implementations never call velo, and the `gdl` crate does not depend on it.

A public transport trait was rejected:

- velo already has what a second transport would exist for: several nodes in one process over TCP, a same-worker attach path, a simulation transport, stop and cancel, open tickets, and mux lanes.
- A trait would cut velo down to a common denominator, or mirror it method for method.
- No second transport exists, and the repository does not add an abstraction for a caller that does not exist.
- velo is before 1.0 and changes quickly. The module boundary holds that churn in one place.

## Typed graph structure

The graph is a typed structure, and the placement is runtime data.

- Each node has a marker type that fixes its role and port types through a declaration trait (`SinkDecl`, `BackwardDecl`, and so on).
- `Bindings` has one slot per node other than the source. A slot holds an implementation or `Absent<N>`, where `N` is the node's marker. A blanket impl per role gives `Absent<N>` exactly its node's port types. One shared placeholder could not be both a `Raw -> Tok` backward node and a `Tok -> Out` one. Every call on it fails with `NotHosted`, and a segment refuses to assemble with a placeholder in a slot it hosts, so none is made.
- A segment that binds only `B`, `C`, and `G` names no other implementation type, so it links nothing else. That is how a CPU-only segment avoids the GPU node's dependencies.
- At each stage boundary, the runtime checks the placement: same segment, call the next stage; other segment, encode and leave. That is one branch per boundary. Inside a run, every call is static. One compiled build can therefore run any placement, and the tests use this to run every placement of the reference graph.

## Byte-based crossings

Every gdl anchor carries velo's byte items, and each edge's codec turns `T` into bytes and back. A runtime that is generic over `T` cannot call velo's `attach_anchor::<T>` without `T: Serialize`, and a runtime check cannot supply that bound. A codec is a pair of function pointers, monomorphized where `T` is concrete (in the graph macro's expansion), so the runtime carries the bound without naming it. An edge whose type cannot be serialized has no codec, and a placement that would cross it is refused before anything runs.

The edge codec writes each item straight into velo's frame, so a crossing adds no copy of the item. The receiver decodes it where it arrived. [Crossing performance](../operations/crossing-performance.md#codec-cost) has the measured cost and the command.

A request's head is written behind room for the rest of its envelope, and the envelope is written into that room when it is offered ([What crosses the wire](../concepts/crossings.md#what-crosses-the-wire)). Before, the head went into a buffer of its own that grew by doubling, and the envelope's encode copied it into a second buffer. A 4 MiB image took an 8 MiB head buffer and a 4 MiB envelope. Three other forms were not taken:

- **A size pass on every head.** It serializes every head twice. With the first buffer of 1 KiB, only a head larger than that is serialized to count it.
- **The head first, and the other fields after it.** It needs no room, but it changes the envelope's layout, so every receiver would need a new envelope version.
- **A size hint from earlier requests,** as a stream's items have. The requests of a hop come from many tasks, so a shared hint is a write to one cache line on each request. A head larger than the hint would still double its buffer.

The first form wrapped the bytes in a `WireItem` enum that velo serialized inside its own frame: two encodes and four copies of the payload per item, against velo's one encode and two copies. It cost 97 ns more than velo per item at 16 B and 477 ns more at 16 KiB, and 3 more allocations per item end to end. A tag byte before each payload, instead of an empty item for Open and velo's sender error for Fail, was not taken: it costs a byte per item and a copy unless the codec writes it.

The graph macro picks a streamed edge's codec from the syntax (`stream_codec!` for `Head + stream Item`, `wire_codec!` otherwise). The wire probe is autoref specialization with two levels. A third autoref level that recognized `Streamed` by type was not built, because the syntax already marks each streamed edge (`Head + stream Item`).

## Who provisions the backward path

The outer end provisions every intermediate backward run before it dispatches the request, and velo's exclusive attach decides which stage writes each anchor. Because the outer end does all the provisioning, a failed opening returns to it as an ordinary error. Dropping its own anchor then cancels every run it already opened, through the stream each one attached. No stage needs to tell another stage that setup failed.

A run that the backward path revisits in the outer end's own segment is opened by a direct call on the outer end's instance, with no unary call.

## Acknowledge after admission

A receiver acknowledges a hand-off only after it has checked the deployment and the deadline and taken admission and egress. There is no fire-and-forget send. The acknowledgement is what moves ownership of the reply to the next stage. A sender that has an acknowledgement knows that it no longer writes the error. A sender that has a refusal still owns the request. It takes an `Overloaded` or `Placement` answer as its offer declined, and offers the request to another instance, or a chooser to another pool. Every refusal returns before the receiver starts the request's task, so a refused request has run nowhere.

## Activation on `Open`, never on data

A provisioned backward run activates on the open signal (an empty item) that its producer sends as soon as its stream exists. Two other triggers fail:

- **Activate at once.** A backward node may legally ignore its input and end at once. It would finish and remove its anchor while the outer end was still provisioning, and the next attach would fail, where a local run would have produced an empty stream.
- **Activate on the first item.** An upstream stream may stay pending forever while a backward node that ignores it ends at once. Waiting for data would hang that run.

The inner end sends `Open` only after its node returns a stream. So a failing `generate` reaches the caller as the call's error, as in local composition, even behind backward nodes that ignore their input (`a_failing_generate_is_not_masked_by_input_ignoring_backward_nodes`).

## Success needs `Finalized`

A crossed stream succeeds only if velo delivered `Finalized`. Every other ending becomes `Truncated`: a detached producer, a dropped sender, and a stream that just ends. velo can end a stream without its terminal frame (an anchor removed by its unattached timeout yields no frame), so only an explicit finish proves that the producer reached its end.

## Deadlines

**Wall clock, not remaining time.** The deadline crosses as absolute wall-clock time. Sending the time remaining would let every delayed hop restart the budget: each hop would start its count from its own arrival, and network delay would never count.

**Early, never late.** Each receiver subtracts `clock_skew` when it converts. With clocks within the skew, a receiver can stop up to two times the skew early, but it never runs past the source's deadline. `remote_deadlines_never_run_late_with_clocks_off_either_way` shifts one instance's clock both ways.

**Every crossing attempt has a deadline.** A forward stage in another segment cannot see a cancel while it runs, and work that no cancel reaches ends only by its deadline. So an attempt without one gets `default_deadline` before it leaves its segment.

**A watcher per remote attempt.** The outer end starts a watcher task when it mints its anchor, not after `Open`. A remote attempt holds another segment's resources on the caller's behalf, so its deadline is enforced whether or not anyone reads the stream. The watcher forwards a stop as it arrives, and at the deadline or cancel drops the anchor itself. It starts at the mint so that a stop reaches the producer during provisioning and dispatch too. It drops the anchor rather than cancel through velo's controller: a cancel through the controller left frames already in the anchor's receive buffer until the stream was read or dropped, so a held, unread stream kept its buffer.

**No timer per local attempt.** A local scope, including a local hop that encloses a remote attempt, enforces its deadline at its boundaries, when its stream is read. An unread `Sleep` never registers, and a timer per local attempt would cost more than the local path spends on an item: about 25 ns, measured with `cargo bench -p gdl-runtime --bench hop` on one aarch64 workstation and a current-thread runtime. A caller that holds a stream unread keeps its own scopes until it reads or drops it. The remote watcher exists because the remote attempt's resources belong to another segment. The enclosing local scopes are the caller's own.

**Checks every 64 ready items.** A producer that is always ready never lets the cancel and deadline futures be polled. Reading the cancel flag and the clock on every item costs more than an item should: a cancel check reads a flag on every scope up to the root, and a clock read is a syscall-class call. So the attempt boundary and the remote pump check every 64 ready items, and a ready producer can overrun by at most that many. The attempt boundary counts them with the run of ready items it already counts for its yield, and checks on the last item of every 64: a second counter cost 4 Ir per item. A wait starts the run again but keeps its place among the 64, so the attempt boundary's next yield comes up to 63 items early. Starting the count again at a wait let a producer that waits every 32 items overrun the deadline without bound: a wait polls the deadline's timer, which fires on a whole-millisecond tick, not the clock (`tests/interval.rs`). Reading the clock at each wait instead cost about 62 Ir per hop for each wait with a deadline, which in a stream that waits between its items is each item.

## Node contexts

A node's context is how the runtime stops the node. A node reports failure with an `Err` item. In an attempt, the inner end runs in its own scope, so a node that cancels its own context gets the same outcome whatever follows it. Under the request scope it shares the request scope, so its own cancel reaches every node under the edge, and the edge reports it when the stream ends. Before that rule, a bare hop's attempt was cancelled where the same hop with a backward node continued (`a_node_that_cancels_itself_is_reported_cancelled_with_or_without_backward_nodes`).

Polling every node's scope on every path was rejected. It would catch a node that misuses its context, at the cost of a check of every scope up the chain, per node per remote item, on the hottest path. The request's deadline still bounds such a node.

**A context's scope takes no lock.** Each context has one scope node: a stop flag, a cancel flag, a pointer to its parent, and a list of the waiters below it. Making, cloning, checking, and dropping a scope take no lock. A check reads the flags of the node and of each node above it: one read for each level, and a hop adds two. A long chain that only its last context holds is dropped in a loop, not by recursion. A context's stop and cancel come from the same parents, so one parent pointer serves both. A child keeps its parents alive, where a cancel token would drop a parent with no handle and move the child up; no one can cancel such a parent, so nothing a caller sees changes.

A waiter, such as `Cx::cancelled` or the attempt boundary's wait, registers on its own node and on each node above it, under each node's lock. A cancel wakes only the waiters registered on the node it cancels, which are the waiters below it. So an attempt that ends wakes nothing outside its own subtree. The flags and a "has had a waiter" bit share one atomic word, changed only by read-modify-write, so a registration and a cancel on the same node always see each other, whichever comes second. A cancel or a stop takes the node's lock only if a waiter has ever registered there. No waker code runs under a lock: wakers are cloned before it and woken or dropped after it, and a waker that panics does not keep the others from their wakes.

**A scope holds its first waiter in place.** Its list holds only the waiters after the first, so a request that waits at one hop allocates nothing to register: its wait is the only waiter on each scope above it. Before, each scope's list allocated on its first waiter, so a request that waited cost one allocation per scope more than one that did not. Whether a request waits can depend on timing. A request that waits for a blocking thread does not wait if the thread finished before the request polls it, which happens more often on a busy host, so a request's allocation count moved with the load on the host (`a_call_that_waits_allocates_what_a_ready_call_does`). A second waiter on one scope still allocates the list, as nested hops that all wait do on the scopes above them, and so does a list that grows past the most waiters it has held. A scope node grows from 48 B to 80 B. Its list is dropped only on a scope that has had a waiter, because dropping it on every scope cost about 20 instructions per scope on every request. The cost is in [Feature costs](../operations/feature-costs.md#stages-in-callgrind-ir). Two other designs were not built:

- **A pool of lists on each thread, reused from scope to scope.** It removes the allocation for every shape after a warm-up, but lists move between threads, and a thread whose pool is empty still allocates.
- **Entries held in the waiter itself, as an intrusive list.** A waiter registers on every scope up to the root, so it would need room for a chain of any depth, and the list would need `unsafe` code.

A request that runs straight through registers nothing. A hop polls its work before its cancel on the first pass (`race_below`), and so does a local runtime hop. The checks inside the work give a cancel that came first its precedence, not the race. The costs move: a check grows with the depth of the chain, and a wait takes one lock for each level where a cancel token takes one. Rejected: keeping tokio's `CancellationToken` for cancel, which takes the token's lock on every create, clone, check, and drop, and allocates a tree node and a place in the parent's list of children for each child context. Also rejected: one `Notify` at the request's root, which stop used. Each attempt cancels its scope when its stream ends, so a request with many attempts in flight would wake every waiter at each end. A loom model checks the node's races (`crates/gdl/src/cx/scope/models.rs`). The cost is in [Feature costs](../operations/feature-costs.md#local-hop).

**A nested hop's future is on the heap.** An operator's future holds the future of the hop it calls, and that one the hops below it. Held inline, the hop above carries all of them, and each request moves them whole. So an operator or a join that is a hop's inner end boxes that future. A sink's future is not boxed: nothing nests below it.

The box is allocated first, and the future is built in it. `Box::pin(f())` builds the future on the stack and then copies it whole into the box: 4,640 B on each request in an endpoint. A function that is kept out of line builds the future, so the compiler gives it the allocation as the place to return into. Inlined, a default release build (16 codegen units) still built the future on the stack. An inner end also returns its node's future, or the box, as it is. An `async fn` around it would copy the request into its own future first (`an_inner_end_adds_no_future_of_its_own`, and `an_operators_future_is_built_on_the_heap`, which reads the release IR in 16 units).

This holds only under an allocator the compiler knows. The compiler writes the future into the box before the call returns only if it knows the box is fresh memory that it may write early: the system allocator's `malloc` says so, and mimalloc, inlined under LTO, does not. There the future is built on the stack and copied once per call, the copy `Box::pin` makes ([Known limitations](../operations/limitations.md#under-an-allocator-the-compiler-does-not-know-a-nested-hops-future-is-copied-into-its-box)). Rejected: passing the box, or a `&mut` to it, into the function that builds the future. For a future, which is not `Unpin`, neither tells the compiler that nothing else points to it, and the copy remained. A write through a raw pointer meets the same rule and needs `unsafe`. Boxing every hop's future, so that a copy moves only a pointer, costs an allocation per hop per request.

Only the future that an operator's `generate` returns is built in its box. A node that returns `.map(..)` on the future of its body hands that future to the combinator by value. The compiler builds it on the stack and copies it whole into the box, with the room it keeps for large awaitees, which nothing has written yet. A node that returns its body's future as it is avoids the copy ([Write nodes](../guides/write-nodes.md#return-an-operators-body-future-as-it-is), `an_operator_that_returns_its_body_future_builds_it_in_place`). Rejected: gdl maps the output itself. It is measured to work: `Box::write(slot, build(make).map(f))` builds the body's future in place inside the box ([Feature costs](../operations/feature-costs.md#an-operators-body-future)). But it needs a second form of `Operator`, a second trait or one more required item, for every operator to carry, to protect a pattern that a node avoids by returning its body's future. That form is also simpler for a node to write.

**A request is moved as few times as it can be.** Each future that takes the request by value copies it into itself, and each future that returns it copies it out again. So a hop is a block, not an `async fn`, which would move the request into a local before using it. Its attempt is built where it is pinned. The forward chain does not return the request to the hop: it hands it on to the rest of the attempt, the inner end and the backward chain, so an empty chain adds no future at all. The `?` operator on a `Result` that holds the request moves it once more, so these places match by hand. A hop's future now holds the request in two places, or three over a sink, where it held three and four (`a_hop_holds_its_request_in_few_places`).

**A source adds no future of its own.** `Source::call` and a source's `generate` return the hop's future itself. As `async` functions, they each wrapped it in one more future, and a caller that awaits a future moves it whole, with the hop's future inside it: at each source, on every request (`a_source_adds_nothing_to_its_hops_future`).

**A node boundary does not copy an item.** `Fuse` and `Bounded`, the boundaries of a local hop, return their inner stream's poll as their own result. The compiler then writes each item once, where the consumer reads it. If the poll is still alive when the boundary calls a function, for example to end the stream, the compiler keeps the poll in a place of its own and copies it out on return: once per item at each boundary, which is four copies of each chunk on an endpoint's two hops. Taking only the error out of the poll is not enough: the rest of the poll is still dropped after the call. So the arms that run on every item only count, and the arms that call (an error, the end, a wait) first give the whole poll to a helper that takes it by value. A call that returns a constant is still a call: the attempt boundary reads whether its first item is still to come before it polls, not in the match. The attempt boundary's ending runs out of line (`finish`), and returns the poll itself. Built in the caller from a returned error, the poll was built aside, as large as the item, and copied whole. The items of a streamed request (`UntilError`) follow the same rule: dropping the input at its error is a call. `tests/codegen.rs` reads the release IR of gdl's `copies` example and fails if any of the three copies an item. Its control is a boundary that keeps the poll alive across a call. The cost is in [Feature costs](../operations/feature-costs.md#copies-of-an-item).

**A hop with no backward node boxes one stream.** Its inner end's stream passes a node boundary (`Fuse`) and then, at once, the hop's attempt boundary (`Bounded`). The attempt boundary is generic over its inner stream: a hop with backward nodes gives it the last node's boxed stream, and a hop with none gives it the inner end's `Fuse` itself, unboxed, in the same field. It polls that `Fuse` directly and drops it where it would drop the box, so each end, drop, and panic path is the two boundaries' own code in the same order. Only the box and its dynamic call go: one allocation and 172 Ir per request, and 15 Ir per item, at each such hop ([Feature costs](../operations/feature-costs.md#stages-in-callgrind-ir)). A distributed hop whose plan is local does the same: its inner end returns its `Fuse` unboxed, and `bound_measured`, the root's attempt boundary, takes it as `bound` does. `Fuse::poll_next` is forced inline: left to the compiler, it stayed a call in the attempt boundary, and the change saved 1 Ir per item. `items::order` runs the same producer through both forms over every way the boundary ends and asserts the same record of polls, waiter registrations, drops, cancels, and panics. Rejected: one boundary that does both jobs in its own code, holding the producer's scope beside the attempt's. It saved about 14 Ir more per item, since each item passes one set of checks instead of two, but three of its end and panic paths came out different from the two boundaries': a clean end checked the attempt before the producer's stream was dropped, a caught panic in that drop left the attempt live, and a panic while building the boundary dropped the producer's scope without cancelling it. Each needed its own fix, and nothing made the next one visible. The tests that found them stay in `tests/boundaries.rs`.

**A call keeps an attempt only where it needs one.** An operator's call of `next` with its own context runs under the request's scope ([Requests](../concepts/requests.md#calls-and-attempts)). The `next` an operator receives (`Called`) holds the operator's own scope node and deadline, and chooses per call: with them unchanged, the hop's pass-through form (`Next::pass`), which has no scope, guard, race, or boundary; otherwise, or when the operator sets `CALL_SCOPE`, the hop's attempt (`Next::generate`). A constant cannot select a type on stable Rust, so the choice is a value, read once per call. The attempt's arm is boxed: unboxed, it sized every operator's boxed future for it, which pushed the box past the allocator's small-size cache and cost a pass-through stage 342 Ir per request. A local plan's `DHop::pass` matches `Hop::pass` and is boxed too, so that the front's call future does not hold every operator's walk (`the_front_call_future_stays_under_its_ceiling`). A remote hop always takes its attempt: its watcher cancels the attempt and ends only with it, and the admission slot and default deadline belong to it.

The request's edge races the scope it hands the stage below it while the request dispatches, and its node boundary checks that scope after it drops the producer's stream. While the stream runs, the edge's attempt boundary watches its attempt. Each choice was tested against its alternative:

- **The edge watching the request scope while the stream runs.** The inner end's own node boundary cancels that scope as cleanup when the inner stream ends, while a backward node may still pass the last items on. A boundary that watched it took that cleanup for a cancel, and 22 of gdl's tests failed. So a node's own cancel of the request scope is cooperative while the request streams.
- **Checking the request scope right after dispatch.** A node that cancels its own context and returns at once would lose its ready items (3 tests). The race alone is enough; its price is that a node that cancels itself and then waits is dropped with no items.
- **`Cancelled` from a call that finds its request over.** A retry or a migration operator then sends the failure that caused the retry, after the request was cancelled. A call under the request scope ends quietly instead, and the edge reports why.
- **One child scope per pass-through hop.** 379 Ir and an allocation per request at each hop, and nothing watches the scope, so a node's own cancel then goes unreported.
- **A yield in every pass-through hop, or a node boundary for every backward node.** 19.76 Ir per item, 268 Ir and an allocation per request, charged to nodes that never filter. A node that filters declares it (`FILTERS`) and pays that alone.
- **Pass-through by call position,** for any nested hop. It breaks a service entry's root visit, which the pipeline's root `DHop` records, and a remote attempt's watcher would outlive the call.
- **Comparing scopes by address alone,** which saves the `Arc` clone in `Called`. A reused address could pass an unrelated root through.
- **The choice in the spec, in a combinator, or a default of today's attempt with an opt-out.** Whether a call needs its own scope depends on the operator's code, which neither the spec nor the composer sees; a node moved to another graph would lose its scope silently. A default attempt keeps the cost on every operator whose author does not know to remove it.

**One attempt boundary for a chain was rejected.** It was tried before the request scope: one attempt boundary for a chain of local operators. The chain's outermost hop would keep the full boundary. Each hop called by an operator marked as trusted would get a shared one, which skips the check every 64 items, its own yield count, and the check of the attempt at a clean end. It would also make its deadline timer only at its first wait. A build that skipped that work saved 11 Ir per item and 90 Ir per request at each operator stage (14 and 252 with a deadline). But each piece of that work is what keeps a stage's outcome the same, and a review found four counterexamples:

- **A clean end.** A producer whose cleanup cancels the attempt is reported as cancelled only by the attempt boundary's check after that cleanup (`a_clean_end_reports_cancellation_from_producer_cleanup`). The node boundary's check comes before it.
- **A deadline inside a filter.** An operator that consumes items without returning any keeps the outermost hop from running. Only the inner hop's own check stops its stream within 64 items of the deadline.
- **A second call of `next`.** A new attempt does not count its items in step with the outer hop. A cancel from above reaches it first through its own check, and the operator receives the `Cancelled` and can handle it. With only the outer hop's check, the outer hop drops the operator instead.
- **A timer made at the first wait.** It belongs to the runtime that polls the stream, not the one that built it. A stream moved to a runtime without timers then panics at its first wait.

Each item of the contract the shared boundary gave up, a 1,024-item reach for a cancel inside the chain, a later deadline inside a trusted operator, and a lost `Cancelled` after a second call, would be a change a stage can see. With every check kept, what is left to skip is the attempt boundary's yield test: per operator stage, 0.3 Ir more per item at one stage and 0.1 Ir less at five, and 3 Ir less per request. What costs is the check of each attempt, and each attempt needs it. Taking the 64-item count from the node boundary's counter, so that the attempt boundary keeps no count of its own, saves about 6 Ir per item. But it couples the two boundaries' counters, and a hop with no backward node would then yield once in 1,024 items, where one with a backward node yields twice.

**An around node's value rides the attempt.** The forward chain hands the request on to the rest of the attempt rather than return it, and the hop builds the backward chain inside that continuation. So every forward half's value is still alive when the backward chain is built. The chain passes it down as a typed stack, a nested tuple: each forward half pushes its value, and each backward half takes the one on top and moves it into the stream it returns. That stream is boxed already, so a hop that uses the slot allocates nothing more than a forward node and a backward node do, and a hop that does not carries `()`, which compiles away (`an_around_node_allocates_what_a_forward_and_a_backward_node_do`, `a_hop_with_an_around_holds_its_request_in_few_places`). Each entry is tagged with its node's type, so a backward half can take only its own node's value. Four other designs were not built:

- **A value in the attempt's context** (`cx.keep`, `cx.take::<T>()`). Every child context would carry a field, so hops that do not use it would pay too. A forward node gets `&Cx`, so a store needs interior mutability and a box. A mismatch would be a `None` at run time, and extensions are cloned into child contexts, so a nested hop's attempts would see their parent's value.
- **A `State` type on `Forward` and `Backward`.** Associated type defaults are not stable Rust, so every node outside the workspace would have to name one.
- **A map keyed by the request.** No response is matched to its request through a map or an id. A retry also keeps its request's id.
- **The value carried in each item.** A copy or a clone per item, on the path that the node exists to make cheaper.

An around node that wraps the rest of its hop as an inner end, as an operator does, needs no stack, but it adds a node boundary and a scope for each pair: the per-item cost the role removes.

**A distributed hop keeps one slot per around node.** One build serves every placement, so the stack's type cannot depend on where the halves run. Each entry is an `Option`, filled where the forward half ran and empty elsewhere. The outer end holds its stack in its own future through the hand-off, an offer to another instance after a decline, and the wait for the open signal, and gives it to the backward run it ends. A hand-off's task gives the stack from its forward walk to the inner end's backward run. A backward run that the outer end opens, and a middle forward run, hold only empty slots. The layout refuses a placement that would leave a backward half an empty slot, so the empty slot that a backward half finds anyway fails its stream with `Placement`, not a panic. Carrying the value across a segment was not built: the backward run is opened before the request leaves, so the value would need a new frame and a new envelope version, and an encode and a decode on every attempt.

**An attempt that is ready at once registers no waiter.** A hop polls its attempt before it waits on the attempt's cancel. An attempt that finishes in that poll never registers on the cancel's waiter list. Later polls check the cancel first, and no poll polls the attempt twice (`a_hop_polls_a_waiting_inner_end_once_a_pass`).

Each attempt spends one unit of tokio's cooperative budget. An operator that retried attempts which failed at once used to loop without yielding, and starved the task that would cancel it. With the budget, such a storm yields about every 128 attempts. The cost per item did not change.

## Admission and egress

**Reentrant admission.** Admission counts root requests, not entries, so one request cannot block itself on its own provisioned run. The ledger is sharded by root and touched only at entry and retirement, so it adds no global lock on the hot path.

**What was tried: an expiring egress quota.** The first egress design held each permit for a grace period after the stream ended, to cover output velo still held. With 1,024 permits and a 5 s grace, it refused benchmark traffic within seconds: it capped an instance at limit / grace requests per second. It also bounded nothing for a consumer that stalls longer than the grace. It was removed. Today the quota bounds streams while they produce, and a finished stream holds its permit until velo reports it retired, bounded by the request's deadline.

**A failure delivery takes no permit.** On a saturated instance, a permit would queue the error behind live traffic, so the consumer would see its deadline instead of the failure. The delivery writes one frame, bounded by the request and the setup timeout before it attaches and by 100 ms after.

**Hold and wait is accepted.** An outer end that holds an input pump's permit while its local inner end waits for another can be refused at the limit. Every wait is bounded, so it is refused, never hung. Provisioned local runs and a local inner end already share one quota the same way.

**Holding until velo retires a stream.** A share released after `finalize` would let a retiring instance exit with output still queued in velo. gdl takes velo's retirement signal (`StreamSender::retired()`), asked for before `finalize` consumes the sender. The pump awaits it in its own task, raced against the request's `done` future that it already holds, so no task or timer is added per stream. Producers that hold no share (an inner end or a backward run that the outer end runs in its own segment, and the outer end's input pump) wait for retirement too. They run under an attempt of the source's body, or of a visit admitted on the instance, and that attempt's response ends before the body returns or the visit's share drops. So the claim an empty ledger makes holds once the source's body has returned, and the lifecycle's exit rule depends on that condition. An acknowledgement from the consumer in gdl's own protocol was measured and rejected. [Lifecycle design](lifecycle-design.md) and [What gdl relies on in velo](velo.md) give the numbers.

## Streamed requests

**The receiver mints the input anchor.** velo binds a reader to the process that minted its anchor: the registry entry, the frame channel, and the mux slot live in the minter, and no API hands a reader to another process. So the stage that reads the items must mint their anchor. The receiver mints it last, after everything that can refuse, so a refusal leaves no anchor behind.

**The input pump starts before `Open`.** A sink may read its input before it returns its stream, and `Open` follows that return. A sender that waited for `Open` first would deadlock with such a sink.

**No request-side `Open`.** Nothing on the request side is provisioned ahead. The receiver exists before its producer, and the acknowledgement already says it is ready.

**A crossed input ends cleanly only on `Finalized`.** rhino-asr, the prior art, treats a dropped sender as a clean end, which turns a lost producer into a short input. gdl ends such an input with a terminal `Err`. Local input is fused at every `Streamed::new`, so local and remote runs give the same outcome.

**The receiver retires its input anchor when its run ends.** Nothing else ends that anchor promptly: a sender whose acknowledgement was lost never attaches, a node may hold its input unread, and velo removes an unattached anchor only after its reservation lifetime (180 s for a prebound one, by default).

**Replay is the operator's job.** `Streamed` is not `Clone`, because its items can be read only once. An operator that retries, hedges, or migrates a streamed request keeps its own copy of the items it needs.

**No cross-direction deadlock detection.** Input pumps run on their own tasks and are never driven by response reads, so the runtime adds no coupling. A deadlock the application builds is bounded by its deadline.

## Stop and the input

A stop does not end the input, as in local composition. Stop reaches the inner end on the response side, then travels back up the request path through velo's control path: a receiving run whose context is stopping asks velo to stop its input anchor. These designs were tried or considered, and dropped:

- **An in-band `Stop` item down the request path.** A `Stop` item is data. It waits behind exhausted credit. A reader that waits for a stop before it reads never sees it. After the input ends, or for a relay that turns a value into a stream, no input pump is left to send it. velo's stop is a control message that no data credit holds back.
- **No watcher on the run's context.** A stop then reached a receiving run only where its own consumer's stop arrived. A stop that a node asked for itself (for example, a sink's forward node) never reached the relay before it, and the request ran to its deadline. The watcher is back, as a task of its own spawned only for a run with an input anchor.
- **A watcher polled with the run.** It would register a cancellation future on every item. In the first measurement, a stop watcher polled on every item changed no throughput figure beyond the run-to-run variation (under 2%), but the separate task keeps it off the item path.
- **A control anchor per attempt**, or an in-band frame down the request path. Either would close the remaining gap (a stop that a relay asks for after its input ended, or just before its run ends), at a cost on every request. That cost was not accepted. The two tests that pin the gap carry the reasoning in their doc comments.

A cancel must not pass as a stop. velo fires a sender's stop token on a cancel too, and a cancel can land between a select's poll of the cancel and its poll of the stop. A pump that took that cancel for a stop would stop what feeds it, the outer end's attempt included. So a pump that sees its consumer's stop first checks whether the consumer cancelled, and treats that as the consumer leaving.

## Pump costs

- A send with room completes in one poll. Only a send that has to wait also watches stop, cancel, and the deadline. So a stalled consumer cannot hold a stage past its deadline, and the common path builds no timer.
- The pump builds its stop, cancel, and deadline futures once per stream. A fresh future registers again when polled, with the runtime's shared timer and the tokens' waiter lists: a lock per item that every stream of the runtime would contend on.
- Reply renewal uses one task per runtime and a sharded map of held reservations, not a timer per request. On the reference benchmarks its cost was below the noise of a 57 µs crossing ([Crossing performance](../operations/crossing-performance.md)).

## Known untested hazards

**A transport that stalls before `Open`.** velo's heartbeat sweep puts heartbeat frames into the same bounded channel as items, with `try_send`. A transport that stalls can fill that channel before the producer sends `Open`. `Open` is sent through the same interruption-aware send as every item, which watches stop, cancel, and the deadline, so such a stage ends at its deadline. Every gdl consumer reads while it waits for `Open`, so a reader that does not read cannot cause the stall. No test stalls the transport before `Open`: the existing stall tests stall the application, not the transport. A plain send here would wait without bound, and no test would fail.
